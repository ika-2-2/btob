## 第II章 — はじめに（Introduction）

このプロジェクトは、仮想化という素晴らしい世界を紹介することを目的としています。

所定の指示に従い、VirtualBox（VirtualBoxを使用できない場合はUTM）で初めての仮想マシンを作成します。このプロジェクトの終了時には、厳格なルールを適用しながら、自分自身でオペレーティングシステム（OS）をセットアップできるようになります。

## 第III章 — AIに関する指示（AI Instructions）

### 背景（Context）

このプロジェクトは、42での学習を支える基本的な構成要素を発見できるよう設計されています。

重要な知識とスキルをしっかり定着させるには、AIツールやその支援の使い方について、よく考えた姿勢を取ることが不可欠です。

真の基礎学習には、挑戦、反復、そして仲間との学習交流を通じた、自分自身の知的な努力が必要です。

AIを学習ツールとして、42での教育の一部として、また就職市場で期待されるものとしてどう捉えるかについては、イントラネット内の専用FAQを参照してください。

### 主なメッセージ（Main message）

- 近道をせず、強固な基礎を築くこと。
- 技術的スキルとパワースキル（対人・問題解決などの能力）を本当に伸ばすこと。
- 仲間同士で学ぶ経験を積み、学び方そのものと、新たな問題を解決する方法を身につけ始めること。
- 学習の過程は、結果よりも重要であること。
- AIに関連するリスクを理解し、よくある落とし穴を避けるための効果的な管理方法や対策を身につけること。

### 学習者のルール（Learner rules）

- 与えられた課題について、特にAIを利用する前に、自分で考えて取り組むこと。
- AIに直接的な答えを求めないこと。
- AIについての42全体の方針を学ぶこと。

### この基礎段階で得られる成果（Phase outcomes）

この基礎段階では、以下を得られます。

- 技術とコーディングの適切な基礎を身につける。
- この段階でAIがなぜ、どのように危険となり得るかを理解する。

### コメントと例（Comments and example）

- もちろん私たちは、AIが存在し、課題を解けることを知っています。しかし、あなたがここにいるのは学ぶためであって、AIが学習済みであることを証明するためではありません。AIが課題を解けるというだけのことを示すために、自分や他の人の時間を無駄にしないでください。
- 42で学ぶということは、答えを知ることではなく、答えを見つける力を育てることです。AIは直接答えを示してくれますが、それによって自分の思考力を育てる機会が失われます。考えることには時間も努力も必要で、失敗も伴います。成功までの道のりは簡単であるべきではありません。
- 試験中はAIを使用できないことを忘れないでください。インターネットもスマートフォンもありません。学習中にAIに依存しすぎていたなら、その影響はすぐに実感するはずです。
- 仲間との学習では、異なる考え方やアプローチに触れられ、対人スキルや多角的に考える力を伸ばせます。これは、ボットとチャットするだけよりもはるかに価値があります。遠慮せずに話しかけ、質問し、一緒に学んでください。
- もちろん、AIは学習ツールとしても学習対象としてもカリキュラムに含まれます。自分自身のAIソフトウェアを作る機会さえあります。段階的にAIを取り入れていく42の方針について詳しくは、イントラネットのドキュメントを参照してください。

**✓ 良い実践例**

> 新しい概念が理解できずに行き詰まった。近くの人にどう取り組んだか尋ね、10分ほど話し合ったところ、突然理解できた。

**✗ 悪い実践例**

> AIをこっそり使い、正しそうなコードをコピーした。相互評価では何も説明できず不合格になった。試験でもAIを使えず、再び行き詰まって不合格になった。

## 第V章 — 必須課題（Mandatory part）

このプロジェクトでは、定められたルールに従って、初めてのサーバーをセットアップします。

> **警告:** サーバーの構築が目的なので、インストールするサービスは必要最小限にします。そのため、グラフィカルインターフェースは不要です。**X.org、Wayland、その他の同等のグラフィックサーバーをインストールすることは禁止されています。違反すると評価は0点になります。**

OSとして、**Debianの最新安定版**（testing/unstable版は不可）、または**Rockyの最新安定版**のどちらかを選択しなければなりません。システム管理の初心者には、Debianを強く推奨します。

> **情報:** Rockyのセットアップはかなり複雑なため、KDumpを設定する必要はありません。ただし、**SELinuxは起動時に動作していなければならず**、このプロジェクトの要件に合うよう設定を変更する必要があります。Debianの場合も、**AppArmorが起動時に動作している必要があります。**

### 1. ディスクと暗号化

**LVMを使用して、少なくとも2つの暗号化されたパーティションを作成**しなければなりません。以下は可能なパーティション構成の例です（原文 p.7 の画像を文字にしたもの）。

```text
NAME             SIZE   TYPE   MOUNTPOINT
sda                8G   disk
├─sda1           487M   part   /boot
├─sda2             1K   part
└─sda5           7.5G   part
  └─sda5_crypt   7.5G   crypt
    ├─wil--vg-root 2.8G  lvm   /
    ├─wil--vg-swap_1 976M lvm  [SWAP]
    └─wil--vg-home 3.8G  lvm   /home
sr0             1024M   rom
```

> この図は構成例です。ディスクサイズや論理ボリューム名はそのまま真似する必要はありません。

### 2. OSについて理解しておくこと

評価（defense）の際には、選択したOSについていくつか質問されます。例えば、`aptitude` と `apt` の違い、SELinuxやAppArmorが何なのかなどです。**要するに、自分が使っているものを理解してください。**

### 3. SSH

仮想マシン内で、**SSHサービスをポート4242で実行**しなければなりません。セキュリティ上の理由により、**rootユーザーによるSSH接続は禁止**しなければなりません。

> **情報:** 評価では新しいアカウントを作成したうえでSSHの動作をテストします。したがって、SSHがどのように動作するか理解しておく必要があります。

### 4. ファイアウォール

OSに **UFW**（Rockyの場合は **firewalld**）を設定し、仮想マシンでは**ポート4242だけを開放**してください。

> **情報:** 図のディスクサイズは任意の例です。正常に動作し、不要なディスク使用を避けられるよう、各パーティションの適切なサイズを決める必要があります。

> **情報:** ファイアウォールは、仮想マシン起動時に有効でなければなりません。Rockyの場合はUFWではなくfirewalldを使ってください。

### 5. ホスト名・ユーザー・グループ

- 仮想マシンのホスト名は、**自分のログイン名の末尾に `42` を付けたもの**にしてください（例：`wil42`）。相互評価中には、このホスト名を変更する必要があります。
- 強力なパスワードポリシーを実装してください。
- 厳格なルールに従って `sudo` をインストール・設定してください。
- `root` ユーザーに加えて、**自分のログイン名と同じユーザー名のユーザー**を作成してください。
- そのユーザーを **`user42` グループと `sudo` グループ**に所属させてください。

> **情報:** 相互評価では、新しいユーザーを作成し、そのユーザーをグループに割り当てる必要があります。

### 6. パスワードポリシー

強力なパスワードポリシーを設定するため、以下の要件をすべて満たす必要があります。

- パスワードの有効期限は **30日**とします。
- パスワードを変更してから次に変更できるまでの最短期間を **2日**に設定します。
- 有効期限の **7日前**に警告メッセージを出します。
- パスワードは **10文字以上**とし、**大文字・小文字・数字**をそれぞれ含めます。また、**同じ文字が4文字以上連続してはいけません**（同一文字の連続は最大3文字）。
- パスワードにユーザー名を含めてはいけません。
- **root以外のユーザー**については、新しいパスワードに、以前のパスワードに含まれていなかった文字を少なくとも**7文字**含める必要があります。この規則のみrootには適用されません。
- もちろん、rootのパスワードも、rootに適用される上記のポリシーに従わなければなりません。

> **警告:** 設定ファイルを用意した後、**rootを含む仮想マシン内の全アカウントのパスワードを変更**しなければなりません。

### 7. sudoの設定

`sudo` グループの設定を安全なものにするため、以下の要件をすべて満たす必要があります。

- `sudo` 使用時に誤ったパスワードが入力された場合、認証試行回数を **3回**までに制限します。
- `sudo` で誤ったパスワードが入力された場合、**自分で決めたカスタムメッセージ**を表示します。
- `sudo` によって実行された**すべての操作をログに記録**します。入力と出力の両方を記録し、ログは **`/var/log/sudo/`** に保存します。
- セキュリティ上の理由から、**TTYモードを有効**にします。
- セキュリティ上の理由から、`sudo` が使用できるパスも制限します。例：

```text
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/snap/bin
```

### 8. 監視スクリプト `monitoring.sh`

最後に、**Bashで書いた `monitoring.sh`** という簡単なスクリプトを作成する必要があります。

サーバー起動時、および**10分ごと**に、このスクリプトは以下の情報を**すべての端末**に表示します（`wall` コマンドを調べてください）。バナーの表示は任意です。エラーメッセージが表示されてはいけません。

スクリプトは、常に以下の情報を表示できなければなりません。

1. OSのアーキテクチャとカーネルバージョン。
2. 物理プロセッサの数。
3. 仮想プロセッサの数。
4. サーバーで現在使用可能なRAM容量と、RAM使用率（%）。
5. サーバーで現在使用可能なストレージ容量と、その使用率（%）。
6. 現在のCPU使用率（%）。
7. 最後に再起動した日時。
8. LVMが有効かどうか。
9. アクティブな接続数。
10. サーバーを利用しているユーザー数。
11. サーバーのIPv4アドレスとMAC（Media Access Control）アドレス。
12. `sudo` プログラムで実行されたコマンド数。

> **情報:** 相互評価では、このスクリプトがどのように動作するかを説明するよう求められます。また、**スクリプト本体を変更せずに、その実行を停止**する必要があります。`cron` を調べてください。

**出力例**（原文 p.10）:

```text
#Architecture: Linux wil 4.19.0-16-amd64 #1 SMP Debian 4.19.181-1 (2021-03-19) x86_64 GNU/Linux
#Physical CPU: 1
#vCPU: 1
#Memory Usage: 74/987MB (7.50%)
#Disk Usage: 1009/2Gb (49%)
#CPU load: 6.7%
#Last boot: 2021-04-25 14:45
#LVM use: yes
#TCP Connections: 1 ESTABLISHED
#User log: 1

```

### 9. 要件確認に使えるコマンドの例

原文 p.11 の画像には、この課題の一部の要件を確認するための例が示されています。画像の例には、当時のDebian 10やRocky 8.7の表示が含まれますが、**インストールすべきOSバージョンの指定ではありません**。

**Rockyの場合（画像内のコマンド）**

```bash
head -n 2 /etc/os-release
sestatus
ss -tulnp
firewall-cmd --list-service
firewall-cmd --list-port
firewall-cmd --state
```

画像の例では、Rocky Linux 8.7、SELinuxが有効（enforcing）、SSHが4242番ポートで待ち受け、firewalldが実行中（running）で、`4242/tcp` が開放されていることを確認しています。

**Debianの場合（画像内のコマンド）**

```bash
head -n 2 /etc/os-release
/usr/sbin/aa-status
ss -tulnp
/usr/sbin/ufw status
```

画像の例では、Debian GNU/Linux 10（buster）、AppArmorモジュールがロード済みであること、SSHが4242番ポートで待ち受けていること、UFWが有効（active）で4242番ポートのIPv4/IPv6通信が許可されていることを確認しています。

## 第VI章 — READMEの要件（Readme Requirements）

Gitリポジトリのルートには、**`README.md`** ファイルを配置する必要があります。READMEの目的は、プロジェクトを知らない人（他の学生、スタッフ、採用担当者など）が、プロジェクトの内容、実行方法、関連する詳しい情報を探す場所をすぐに理解できるようにすることです。

`README.md` には、少なくとも次の項目を含める必要があります。

- **最初の1行**はイタリック体で、次の英文にしてください。

  ```markdown
  *This project has been created as part of the 42 curriculum by <login1>[, <login2>[, <login3>[...]]].*
  ```

- **`Description` セクション:** プロジェクトの目標と簡単な概要を含め、プロジェクトをわかりやすく説明します。
- **`Instructions` セクション:** コンパイル、インストール、実行について、該当する情報を記載します。
- **`Resources` セクション:** 関連する基本的な参考資料（公式ドキュメント、記事、チュートリアルなど）を列挙します。また、**AIをどのように使ったか、どのタスクやプロジェクトのどの部分で使用したか**を説明します。

プロジェクトによっては、追加のセクション（使用例、機能一覧、技術的な選択など）が必要になる場合があります。

必要な追加事項は、以下に明示します。

- **プロジェクトの説明（Project description）**には、DebianとRockyのどちらを選んだか、またそれぞれのメリット・デメリットも説明しなければなりません。セットアップ時の主要な設計上の選択（パーティション分割、セキュリティポリシー、ユーザー管理、インストールしたサービス）を説明し、次の項目を比較してください。
  - Debian と Rocky Linux
  - AppArmor と SELinux
  - UFW と firewalld
  - VirtualBox と UTM

> **情報:** READMEの言語としては英語を推奨しますが、キャンパスの主要言語を使用することもできます。

> **警告:** ボーナス課題は、**必須課題が完璧（PERFECT）な場合に限り**評価されます。「完璧」とは、必須課題をすべて完了し、不具合なく動作することです。必須要件を**すべて**満たしていなければ、ボーナス部分は一切評価されません。

## 第VIII章 — 提出と相互評価（Submission and peer-evaluation）

Gitリポジトリのルートに提出する必要があるのは、指定された **`README.md`** と **`signature.txt`** の2つだけです。

`signature.txt` には、仮想マシンの**仮想ディスクの署名**を貼り付ける必要があります。署名を取得するには、最初に仮想マシンの保存先であるデフォルトのインストールフォルダを開きます。

- **Windows:** `%HOMEDRIVE%%HOMEPATH%\VirtualBox VMs\`
- **Linux:** `~/VirtualBox VMs/`
- **Mac M1:** `~/Library/Containers/com.utmapp.UTM/Data/Documents/`
- **macOS:** `~/VirtualBox VMs/`

次に、仮想マシンの **`.vdi` ファイル**（UTMを利用する場合は **`.qcow2` ファイル**）から、**SHA-1形式**で署名を取得します。

以下は `rocky_serv.vdi` を例にした4つのコマンドです。

**Windows:**

```powershell
certUtil -hashfile rocky_serv.vdi sha1
```

**Linux:**

```bash
sha1sum rocky_serv.vdi
```

**Mac M1:**

```bash
shasum rocky.utm/Images/disk-0.qcow2
```

**macOS:**

```bash
shasum rocky_serv.vdi
```

取得できる出力の例:

```text
6e657c4619944be17df3c31faa030c25e43e40af
```

> **情報:** 仮想マシンを再び起動すると、仮想マシンの署名が変更されます。すべての評価で署名を検証できるようにするには、仮想ディスクファイルを複製するか、評価ごとにスナップショットを使うことができます。

> **警告:** **仮想マシンそのものをGitリポジトリに含めることは絶対に禁止**です。評価時には、`signature.txt` に記載された署名と仮想マシンの署名が比較されます。**一致しなければ評価は0点**です。

### スナップショットに関する制約

スナップショットの使用には制約があります。

- 各評価は、**スナップショットが存在しない状態**で開始しなければなりません。
- その後、**評価専用のスナップショット**を作成し、評価終了時に削除します。
- 提出前にスナップショットの機能を試しておくことを推奨します。

### 評価中の小さな変更

評価中、プロジェクトに対して短時間で行える変更を求められる場合があります。たとえば、動作を少し変える、コードを数行書く・書き直す、簡単な機能を追加する、といった変更です。

すべてのプロジェクトにこの手順が適用されるとは限りませんが、評価ガイドラインに記載されている場合は対応できるよう準備しておく必要があります。

この手順の目的は、プロジェクトの特定の部分について、あなたが本当に理解しているか確認することです。変更は、通常使っている環境など、好きな開発環境で実施できます。評価ガイドラインに特別な制限時間が定められていない限り、数分で完了できる内容であるはずです。

例えば、関数やスクリプトを少し更新する、表示内容を変更する、新たな情報を保存するためにデータ構造を調整する、といったことが考えられます。

具体的な範囲や対象などは評価ガイドラインに記載され、同じプロジェクトでも評価ごとに異なる可能性があります。
